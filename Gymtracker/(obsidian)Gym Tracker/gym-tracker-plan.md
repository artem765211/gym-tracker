# Трекер силовых тренировок: план курсовой

## 1. Идея проекта

Веб-приложение, в котором пользователь планирует дни тренировок и выбирает упражнения из справочника, при желании вносит результаты, видит свой прогресс по месяцам в процентах и считает КБЖУ. Данные хранятся на сервере и привязаны к аккаунту, поэтому вводить их заново не нужно. Приложение должно удобно работать с телефона, потому что приложением пользуются прямо в зале.

## 3. Функции (текущий объём)

### Ядро
- [ ] Регистрация, вход, выход
- [ ] Справочник упражнений (общие и свои)
- [ ] Планирование тренировок: клиент сам выбирает день и упражнения из справочника (создание, просмотр, изменение, удаление)
  - тренировка = день + список упражнений, без ввода каждого подхода и без отметки «выполнено»
- [ ] Вкладка «Сила»: один лучший подход по упражнению (вес и повторения), значения подставляются с прошлого раза; тренировки без результатов видны в списке «Не заполнено»
- [ ] Вкладка «Прогресс»: расчётный максимум (1RM) по упражнению и процент прироста к прошлому месяцу (только по упражнениям с введёнными результатами)
  - карточки по упражнениям («+4,2% к прошлому месяцу»), график 1RM по месяцам, таблица месяц к месяцу (разница в кг и в %)
  - пока данных меньше чем за два месяца, показывается подсказка вместо графика
- [ ] Вкладка «КБЖУ»: замеры тела (вес, рост, дата рождения, пол, уровень активности, цель) и расчёт КБЖУ по ним

### Отложено (только если останется время)
- личные рекорды (PR)
- «повторить прошлую тренировку»
- подробный ввод всех подходов (таблица WorkoutSet)
- график веса тела
- экспорт в CSV
- refresh-токены
- PWA (установка на экран телефона, офлайн-ввод)

## 4. Формулы

**1RM (формула Эпли):**
`1RM = вес × (1 + повторения / 30)`
Нужна, чтобы 100 кг на 3 повторения и 100 кг на 10 повторений не считались одинаковой нагрузкой.
Считается по лучшему подходу упражнения (`TopWeight`, `TopReps`); остальные подходы на прирост не влияют.

**Прирост за месяц, %:**
`(лучший 1RM этого месяца − лучший 1RM прошлого месяца) / лучший 1RM прошлого месяца × 100`

**Базовый обмен (Миффлин — Сан-Жеор):**
- мужчины: `10 × вес(кг) + 6,25 × рост(см) − 5 × возраст + 5`
- женщины: `10 × вес(кг) + 6,25 × рост(см) − 5 × возраст − 161`

**Суточная норма калорий:** базовый обмен × коэффициент активности (от 1,2 до 1,9), затем дефицит (около 10-20%) для похудения или профицит (около 10-15%) для набора массы.

**БЖУ:** белки примерно 1,6-2,2 г на кг веса, жиры примерно 0,8-1 г на кг, остаток калорий идёт в углеводы.

В интерфейсе указать, что это ориентировочный расчёт, а не медицинская рекомендация.

## 5. Структура решения

```
GymTracker/
├── GymTracker.Api/             контроллеры, DTO, Program.cs, middleware
├── GymTracker.Core/            сущности, интерфейсы, бизнес-логика (1RM, прирост, КБЖУ)
├── GymTracker.Infrastructure/  EF Core, DbContext, миграции, Identity
├── GymTracker.Tests/           xUnit
├── gym-tracker-web/            React-приложение
└── docker-compose.yml
```

Правило зависимостей: `Core` не знает ни про EF, ни про ASP.NET. Интерфейсы лежат в `Core`, реализации в `Infrastructure`. Это пригодится для описания DI и SOLID в тексте курсовой.

## 6. Модель данных (набросок)

- **User** (из Identity): Id, UserName, Email
- **BodyMeasurement**: Id, UserId, Date, Weight, Height, BirthDate (дата рождения; возраст считается в момент расчёта), Sex, ActivityLevel, Goal
- **Exercise**: Id, Name, MuscleGroup, UserId (пусто для общих упражнений)
- **Workout**: Id, UserId, Date, Note
  - статуса «выполнено» нет: прошедшие тренировки без результатов попадают в список «Не заполнено»
- **WorkoutExercise**: Id, WorkoutId, ExerciseId, TopWeight (необязательно), TopReps (необязательно)

Заметки по PostgreSQL:
- пакет `Npgsql.EntityFrameworkCore.PostgreSQL`
- для даты тренировки лучше `DateOnly`; `DateTime` для `timestamptz` должен иметь `Kind = Utc`
- вес хранить как `numeric` с заданной точностью, а не `double`; повторения как `int`

## 7. REST API (набросок)

| Группа | Эндпоинты |
|---|---|
| Авторизация | `POST /api/auth/register`, `POST /api/auth/login` |
| Упражнения | `GET /api/exercises`, `POST /api/exercises` |
| Тренировки | `GET /api/workouts` (фильтр по датам, пагинация, `?unfilled=true` для списка «Не заполнено»), `GET /api/workouts/{id}`, `POST` (дата и список упражнений), `PUT /{id}`, `DELETE /{id}` |
| Результаты | `PATCH /api/workouts/{id}/exercises/{exerciseId}` (вес и повторения) |
| Прогресс | `GET /api/progress/exercises/{id}`, `GET /api/progress/summary` |
| Замеры тела | `GET /api/body-measurements`, `POST /api/body-measurements` |
| Питание | `GET /api/nutrition/calculate` |

Правила:
- всё, кроме регистрации и входа, закрыто `[Authorize]`
- `UserId` берётся из токена, а не из тела запроса
- каждый запрос к данным фильтруется по текущему пользователю (защита от IDOR)
- DTO вместо сущностей EF
- коды: 201 + `Location` при создании, 204 при удалении, 400/422 при ошибке валидации, 401 и 403 различать, 404 для чужих и несуществующих ресурсов
- единый формат ошибок (Problem Details), глобальный обработчик исключений

## 8. Технологии фронтенда

- Vite + React + TypeScript (типы API генерировать из Swagger через `openapi-typescript`)
- React Router: страницы и защита приватных маршрутов
- TanStack Query: запросы к API, кеш, состояния загрузки и ошибок
- React Hook Form + Zod: формы и валидация
- Recharts: графики (готовые обёртки есть в shadcn/ui)
- Tailwind CSS + shadcn/ui: компоненты (Drawer, Sheet, Tabs, Sonner), иконки `lucide-react`
- один шрифт (Inter или Geist) и один акцентный цвет
- запасной вариант, если Tailwind окажется тяжёлым: Mantine

Экраны: вход и регистрация; четыре вкладки: «План» (календарь, выбор упражнений), «Сила» (ввод лучшего подхода, список «Не заполнено»), «Прогресс» (карточки по упражнениям, график и таблица по месяцам, процент прироста), «КБЖУ» (замеры тела и расчёт по ним).

Требования к мобильной версии:
- mobile-first вёрстка, тег viewport
- кнопки и поля не меньше примерно 44×44 px, шрифт в полях не меньше 16px
- цифровая клавиатура для чисел (`inputMode="decimal"`)
- минимум ввода: значения с прошлой тренировки подставлены, шаги +2,5 кг и +1 повторение
- нижняя навигация из четырёх вкладок: План, Сила, Прогресс, КБЖУ (выход и профиль в меню в шапке)
- тёмная тема по умолчанию (удобна в зале)
- ввод результата через нижнюю панель (Drawer)
- проверка на реальном телефоне (Vite с `--host`)

## 9. Технические моменты

- **CORS:** React и API на разных адресах, в API разрешить источник фронтенда. `UseCors` ставится до `UseAuthentication` и `UseAuthorization`. Разрешать конкретные источники, а не `*`.
- **Токен на клиенте:** `localStorage` проще, но уязвим к XSS; `HttpOnly` cookie безопаснее, но нужна защита от CSRF. Для курсовой допустим первый вариант, ограничение описать в тексте.
- **Секреты:** пароль БД и ключ подписи JWT в `.env` или user-secrets, не в репозитории.
- **Валидация:** обязательно на сервере, на клиенте для удобства.
- **Порядок middleware:** обработчик исключений, HTTPS, routing, CORS, аутентификация, авторизация, endpoints.
- **Docker:** сначала только PostgreSQL (с volume и healthcheck), API и React запускать локально. Контейнеры для API и фронтенда добавить в конце.

# Gymtracker: инструкции для агента

Курсовая: веб-приложение «трекер силовых тренировок» (мобильная версия в браузере).
Полный план: `gym-tracker-plan.md` (в корне репозитория). Читай его только когда нужны детали, целиком не пересказывай.

## Структура решения (один .sln, четыре проекта)
- `Gymtracker.Api`: контроллеры, DTO, Program.cs
- `Gymtracker.Core`: сущности, перечисления, калькуляторы (1RM, прирост, неделя, возраст, КБЖУ). Без ссылок на EF Core и ASP.NET.
- `Gymtracker.Infrastructure`: `AppDbContext`, миграции, Identity
- `Gymtracker.Tests`: xUnit. Юнит-тесты калькуляторов в `Calculator/`, интеграционные в `Integration/`.
- Зависимости: Api -> Core, Infrastructure; Infrastructure -> Core; Tests -> Core, Api, Infrastructure (Api и Infrastructure нужны для интеграционных тестов).
- Фронтенд по плану будет в папке `gym-tracker-web/` в корне репозитория (ещё не создан).

## Стек
ASP.NET Core Web API (C#, net10.0), PostgreSQL 16 в Docker, EF Core (Code First) + Npgsql,
Identity + JWT, xUnit + Testcontainers, Swagger. Фронтенд (с недели 6): React + Vite + TypeScript + Tailwind + shadcn/ui.

## Правила кода
- В API отдаём DTO, а не сущности EF.
- `UserId` берём из токена, не из тела запроса. Каждый запрос к данным фильтруем по текущему пользователю.
- Всё, кроме регистрации и входа, закрыто `[Authorize]`.
- Ошибки: Problem Details, коды 201/204/400/401/403/404.
- Вес храним как `decimal`, даты тренировок как `DateOnly`.
- Упражнения с собственным весом (подтягивания и т.п.) пока в справочнике не используем.

## Секреты

- В user-secrets лежат строка подключения `ConnectionStrings:DefaultConnection` и ключ подписи `Jwt:Key`.

## Команды (Windows, корень репозитория)
Мой терминал: PowerShell. Команды для меня пиши под него.
- `docker compose up -d`: поднять PostgreSQL (сначала должен быть запущен Docker Desktop)
- `dotnet build` / `dotnet test` (для интеграционных тестов должен быть запущен Docker Desktop)
- `dotnet run --project Gymtracker.Api --launch-profile http`: запустить API, Swagger на `http://localhost:5036/swagger`
- `dotnet ef migrations add Name --project Gymtracker.Infrastructure --startup-project Gymtracker.Api`
- `dotnet ef database update --project Gymtracker.Infrastructure --startup-project Gymtracker.Api`
- Если сборка падает с MSB3027 (файл занят) или порт 5036 занят, API уже запущен в Rider или терминале: попроси меня его остановить.

## Заметки для агента
- Docker Desktop иногда не запущен (после перезагрузки). Тогда база недоступна, а интеграционные тесты падают: попроси меня запустить его, сам не запускай.
- `.claude/launch.json` (конфигурация `api` для превью) запускает API с `--no-build`: перед запуском сделай `dotnet build`.
- После `migrations add` выполняй `database update` без `--no-build`, иначе новая миграция не попадёт в сборку.
- Изменения API проверяй запросами на запущенном API, а новые тесты проверяй на падение (временно сломать код, увидеть красный тест, вернуть и убедиться через `git diff`, что код не изменился).
- Папку `.claude/` не коммитим, в `git add` указывай пути явно.

## Состояние
Готово (бэкенд закончен, недели 1-5):

- Неделя 3: Identity, внешние ключи `UserId` на `AspNetUsers`, JWT (срок 12 часов, refresh-токенов нет), `POST /api/auth/register` (201) и `/login` (200),
  Swagger UI с Authorize, Problem Details, глобальный обработчик исключений, CORS для `http://localhost:5173`.
- Неделя 4:
  - Упражнения: `GET /api/exercises`, `GET /api/exercises/{id}`, `POST`, `DELETE /{id}` (только свои личные; 403 для общих, 404 для чужих, 400 если есть в тренировках или рабочих весах).
  - Тренировки: `POST /api/workouts`, `GET /{id}`, `GET ?from=&to=` (обе даты обязательны), `PUT /{id}`, `DELETE /{id}`.
  - Уникальные индексы: (`UserId`, `Date`) и (`WorkoutId`, `ExerciseId`).
- Неделя 5:
  - `PATCH /api/workouts/{id}/exercises/{exerciseId}`: запись рабочего веса в тренировке (0,01-1000), возвращает обновлённое упражнение (200).
  - Рабочие веса (`StrengthRecord`): `GET /api/strength-records?exerciseId=` (фильтр необязательный, сначала новые) и `PUT /api/strength-records` (создаёт или заменяет, всегда 200; вес 0,01-1000, повторения 1-1000).
  - Прогресс: `GET /api/progress/exercises/{id}` (все месяцы с записями для графика и таблицы, 404 для чужого упражнения) и `GET /api/progress/summary` (карточки: последний месяц с записями по каждому упражнению). Расчёт в `ProgressCalculator.ByMonth`.
  - Замеры тела: `GET /api/body-measurements` (сначала новые) и `POST` (201 без заголовка `Location`, потому что `GET /{id}` нет). Уникальный индекс (`UserId`, `Date`).
  - КБЖУ: `GET /api/nutrition/calculate` (калории, белки, жиры, углеводы и дата замера). Без замеров 404, при нулевых или отрицательных калориях 400.
  - Тесты: всего 53 (43 юнит-теста калькуляторов и 10 интеграционных). Интеграционные в `Gymtracker.Tests/Integration`: временная база через Testcontainers и API внутри теста через `WebApplicationFactory` (`ApiFactory`, общий на все классы через `[Collection("Api")]`; помощник `CreateAuthorizedClientAsync` регистрирует пользователя и даёт клиента с токеном).
    Проверяют: API подключён к временной базе, 401 без токена (тренировки, прогресс), регистрацию, вход, неверный пароль, чужую тренировку (404),
    повторную дату тренировки (400), замену рабочего веса за ту же неделю последним значением, прогресс «март к январю».

Принятые решения:
- Одна тренировка на день у пользователя (проверка в API и уникальный индекс в БД). Повторная дата даёт 400.
- Личные упражнения можно удалять. Изменение пока не делаем.
- Тренировки и рабочие веса (вкладка «Сила») независимы. В `WorkoutExercise` есть только необязательный `WorkingWeight`, повторений там нет, на прирост он не влияет.
- Рабочие веса ведём отдельно: одна запись на упражнение в неделю (вес и повторения), повторный ввод за неделю заменяет старый, даже если результат хуже (так можно исправить ошибку ввода). Заполнять необязательно, на вкладке видны все упражнения.
- Неделя хранится как дата её понедельника: клиент присылает любую дату, сервер приводит её к понедельнику. Прошлые недели записывать можно, будущие нельзя (400), текущую дату берём с сервера. Подстановка прошлых значений на фронтенде идёт из истории `GET`, отдельный эндпоинт не нужен.
- Прирост и 1RM считаем только по рабочим весам. Списка «Не заполнено» нет.
- Прогресс: неделя относится к месяцу своего понедельника, за месяц берём лучший 1RM (округление до двух знаков). Месяц сравниваем с ближайшим предыдущим месяцем, где есть записи (март с январём, если в феврале пусто), и возвращаем его в `previousMonth`, чтобы интерфейс показывал, что с чем сравнивается. У первого месяца поля сравнения равны `null`.
- Замеры тела: один замер в день (повторная дата даёт 400), вес 20-500 кг, рост 50-300 см, возраст 10-120 лет (калькулятор не работает с возрастом 0), дата замера не в будущем, дата рождения раньше даты замера.
- КБЖУ считаем по замеру с самой поздней датой, а возраст на сегодня, а не на дату замера.
- Перечисления в JSON передаём словами (`"Male"`, `"Moderate"`, `"Lose"`), числа не принимаем. Настройка общая для API, в `Program.cs`.
- Тренировки показываем календарём, он сразу открывается на текущем месяце (сделать на фронтенде). Пагинации нет: календарь запрашивает месяц через фильтр по датам.
- `PUT` тренировки сохраняет рабочий вес у оставшихся упражнений; у убранных он удаляется.

Что важно знать фронтенду об API:
- Адрес API в разработке: `http://localhost:5036`. Описание OpenAPI для генерации TS-типов: `http://localhost:5036/openapi/v1.json`.
- Токен передаётся в заголовке `Authorization: Bearer <токен>`, живёт 12 часов; по истечении API отвечает 401, нужно снова войти.
- JSON в camelCase. Даты строкой `"2026-03-10"`, месяцы прогресса строкой `"2026-03"`, перечисления словами.
- Ошибки в формате Problem Details: текст для пользователя в `detail`. Ошибки встроенной валидации приходят в `errors` (по полям, на английском).
